8 Concurrency

Algol 68 was one of the first languages to include concurrency in its definition. A program can ask for several parts of itself to run at the same time, and the parts can coordinate with semaphores, the synchronization primitive that Edsger Dijkstra had introduced a few years earlier. This chapter presents the two constructs, par and sema, and uses them to solve three classic problems.

Implementation note.  Concurrency is the part of the language where the implementations differ most. Algol 68 Genie runs the units of a par clause in threads of the operating system. ga68 currently runs them one after the other, which the Report allows, and does not yet support semaphores. a68j runs them in threads when given the option -fpar-threads, and supports semaphores only with that option; without it, a program that uses LEVEL is rejected (“no lowering routine installed”). The examples of this chapter were run with Algol 68 Genie and with a68j.

8.1 The problems

Two problems arise as soon as parts of a program run at the same time and share data. The first is mutual exclusion. If two parts both execute total +:= 1 on the same variable, each reads the old value, adds one and stores the result; if both read before either stores, one increment is lost. A sequence of operations that must not be interleaved with another such sequence is a critical section, and the program needs a way to let only one part at a time enter it.

The second problem is communication. One part, the producer, computes values that another part, the consumer, needs. The consumer must wait until a value is available, and if the values are passed through a buffer of limited size, the producer must wait until there is room.

8.2 Concurrent execution

A list of expressions in parentheses, preceded by par, is a concurrent block (parallel clause). Its expressions may be evaluated at the same time:

int a, b;
par (a := 6 * 7, b := 2 ** 10);       { two units, possibly at the same time }
print ((whole (a, 0), " ", whole (b, 0), newline))
42 1024

The par clause ends when all its expressions have ended; it has no value. The expressions of an ordinary list may also be interleaved (Section 3.4). What par adds is that each of its expressions is a separate process: one of them can wait on a semaphore while the others go on. Waiting outside a par clause has no other process to wait for; the Report leaves it undefined, and Algol 68 Genie rejects DOWN and UP outside a par clause altogether.

A par clause has a fixed number of expressions. A variable number of processes is started by recursion, each level starting one worker and the rest of the range:

int n = 6;
[n] int squares;
proc worker = (int i) void: squares[i] := i * i;
proc spawn = (int lo, hi) void:
   if lo = hi then worker (lo)
   else par (worker (lo), spawn (lo + 1, hi))
   fi;
spawn (1, n);
for i to n do print ((whole (squares[i], 0), " ")) od;
print (newline)
1 4 9 16 25 36

Each worker writes only its own element of squares, so the workers need no coordination, and the program prints 1 4 9 16 25 36.

8.3 Semaphores

A semaphore is a counter that is changed only by two indivisible operations. The type is sema, and a semaphore is created with the operator LEVEL, which also gives its initial value: sema mutex = LEVEL 1. The operations are unary operators:

  • DOWN s waits until the counter of s is greater than zero and then decreases it by one. Dijkstra called this operation P; in today’s libraries it is called acquire or wait.

  • UP s increases the counter by one, which may let a waiting part continue. Dijkstra called it V; today it is release or signal.

LEVEL s also gives the current value of the counter. A semaphore whose counter is 0 or 1 is a lock (a mutex); a semaphore with a larger counter limits the number of parts that may pass at the same time.

The standard library declares sema as a record with a single field that is a reference to an int, and LEVEL n allocates the counter on the heap. A copy of a semaphore therefore shares the counter, like the records with reference fields of Section 7.11:

sema a = LEVEL 2;
sema b = a;                  { the same counter, not a copy of it }
par (DOWN b, skip);
print ((whole (LEVEL a, 0), newline))
1

prints 1. This is what makes it possible to pass a semaphore to a procedure. A semaphore that was declared without LEVEL, such as an element of [5] sema forks, holds no counter, and using it is a run-time error; that is why the programs below initialize every semaphore. UP lets all waiting parts compete for the counter again; which one gets it is not specified, so a part may in principle wait forever while others pass.

Note that LEVEL, like every unary operator, binds more tightly than any binary operator: LEVEL n - 1 means (LEVEL n) - 1, which is not defined. The initial value n - 1 must be written in parentheses, as in the last program of this chapter.

8.4 Mutual exclusion

The following program lets three concurrent parts each add 100 000 to a shared total. Each increment is a critical section, protected by the semaphore mutex:

int total := 0;
sema mutex = LEVEL 1;
proc add = (int n) void:
   to n do
      DOWN mutex;          { enter the critical section }
      total +:= 1;
      UP mutex             { leave it }
   od;
par (add (100000), add (100000), add (100000));
print ((whole (total, 0), newline))
300000

Without the DOWN and UP, the result would usually be smaller than 300 000, and different from run to run, since increments would be lost when two parts interleave. Such an error is called a race condition; it is the classic problem of concurrent programming, and it is hard to find precisely because it does not show up on every run.

The program takes the lock 300 000 times, which costs time and makes the parts wait for each other most of the time. Parts that share nothing need no lock at all, so the better design lets each part count in a variable of its own and takes the lock only once, to add its result:

int total := 0;
sema mutex = LEVEL 1;
proc add = (int n) void:
begin
   int mine := 0;                     { private to this part }
   to n do mine +:= 1 od;
   DOWN mutex; total +:= mine; UP mutex
end;
par (add (100000), add (100000), add (100000));
print ((whole (total, 0), newline))
300000

A critical section should be as short as possible and should do no more than the shared data require.

8.5 Producer and consumer

The second program passes values from a producer to a consumer through a buffer with room for four values. Three semaphores coordinate the two parts: free counts the free places, full the filled ones, and mutex protects the buffer and its two positions.

access Genie_Transput
begin
   { A producer and a consumer that communicate through a bounded buffer. }
   int size = 4;
   [0 : size - 1] int buffer;
   int head := 0, tail := 0;
   sema free = LEVEL size,     { the number of free places }
        full = LEVEL 0,        { the number of filled places }
        mutex = LEVEL 1;
   proc put = (int value) void:
   begin
      DOWN free;
      DOWN mutex; buffer[tail] := value; tail := (tail + 1) MOD size; UP mutex;
      UP full
   end;
   proc get = int:
   begin
      DOWN full;
      DOWN mutex; int value = buffer[head]; head := (head + 1) MOD size; UP mutex;
      UP free;
      value
   end;
   int n = 20;
   int sum := 0;
   par (
      for i to n do put (i * i) od,           { the producer }
      to n do sum +:= get od                  { the consumer }
   );
   print (("sum of the first ", whole (n, 0), " squares: ", whole (sum, 0),
           newline))
end
sum of the first 20 squares: 2870

put waits for a free place, stores the value and signals a filled place; get does the opposite. If the producer is faster, it waits in DOWN free when the buffer is full; if the consumer is faster, it waits in DOWN full when the buffer is empty. Today’s languages offer the same structure ready-made as a blocking queue or a channel, but it is built from exactly these parts.

The order of the two DOWNs in put matters. If the producer took mutex first and then waited in DOWN free for a free place, it would wait while holding the lock, and the consumer, which needs the lock to make a place free, could never get it: a deadlock. The rule is to wait for a resource before taking the lock that protects it, and to hold the lock for as short a time as possible.

8.6 The dining philosophers

Dijkstra’s best-known synchronization problem has five philosophers sitting at a round table, with one fork between each two of them. A philosopher alternately thinks and eats, and needs both neighboring forks to eat. If every philosopher picks up the left fork first and then waits for the right one, all five may end up holding one fork each and waiting forever, a deadlock.

One simple solution is a butler who lets at most four philosophers sit at the table at the same time. Then at least one of them can always get both forks. In the program, each fork is a semaphore with the initial value 1, and the butler is a semaphore with the initial value 4:

access Genie_Transput
begin
   { The dining philosophers, with a butler who admits at most four at a time. }
   int n = 5, meals = 1000;
   [0 : n - 1] sema fork;
   [0 : n - 1] int eaten;
   for i from 0 to n - 1 do fork[i] := LEVEL 1; eaten[i] := 0 od;
   sema butler = LEVEL (n - 1);
   proc philosopher = (int i) void:
      to meals do
         DOWN butler;
         DOWN fork[i]; DOWN fork[(i + 1) MOD n];
         eaten[i] +:= 1;                              { eat }
         UP fork[(i + 1) MOD n]; UP fork[i];
         UP butler                                    { think }
      od;
   par (philosopher (0), philosopher (1), philosopher (2),
        philosopher (3), philosopher (4));
   for i from 0 to n - 1 do print ((whole (eaten[i], 0), " ")) od;
   print (newline)
end
1000 1000 1000 1000 1000

Each philosopher eats 1000 times and counts the meals in its own element of eaten, which no other philosopher changes; the counts are printed after the par clause has ended. Without the butler, the program could hang.

Exercises

The answers are at the end of the book.

  1. What is the difference between (a, b) and par (a, b)?

  2. What happens if a program executes DOWN s on a semaphore declared as sema s = LEVEL 0, and no other part ever executes UP s?

  3. Is the semaphore mutex of the producer and consumer program necessary as long as there is exactly one producer and one consumer? When does it become necessary?

  4. Give another solution of the dining philosophers that needs no butler. (Hint: let one philosopher pick up the forks in the other order.)

  5. What happens to the producer and consumer program if the two DOWNs in put are exchanged, when the producer is faster than the consumer?

  6. Why does sema b = a; par (DOWN b, skip) change LEVEL a?

Programming problems

  1. Compute the sum of the elements of a large array with four concurrent parts, each summing a quarter.

  2. Build a pipeline of three stages, each a concurrent part connected to the next by a buffer: the first generates numbers, the second squares them, the third prints them.

  3. Implement a semaphore-protected counter as a record with a sema field and the procedures increment and value.

  4. A channel type. Define a record type for a bounded buffer (a reference to an array, references to the two positions, and three semaphores) with procedures send and receive, so that several pipelines can be built from one definition.

  5. Readers and writers. Several parts read a shared table and some change it. Readers may read at the same time, but a writer needs the table to itself. Solve it with semaphores, and think about whether a writer can be kept waiting forever.

  6. A barrier. Build a barrier for n processes from semaphores: no process continues past it until all have reached it. Make it reusable.

  7. Two resources. Two processes each need a printer and a scanner. Show how they can deadlock, and avoid it by acquiring the resources in a fixed order.

  8. Parallel merge sort. Sort an array with merge sort in which the two halves are sorted in a par clause, down to a given depth, and compare the time with the sequential version.

  9. A prime sieve pipeline. Generate the primes with a pipeline of processes: each process holds one prime, passes on the numbers it does not divide, and starts a new process for the first number that reaches it.
