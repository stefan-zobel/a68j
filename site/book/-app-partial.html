Appendix F: Partial parametrization

Section 7.16 showed that an Algol 68 function cannot be returned from the block whose names it uses: a function that composes two other functions, the everyday closure of current languages, is an error. Soon after the Revised Report, Lindsey proposed an extension that removes most of this limitation without changing the lifetime rule [6]. The subcommittee of IFIP Working Group 2.1 that looked after Algol 68 released it in 1976, so that implementations that experimented with such a facility would all provide it in the same form; it is not part of the Revised Report. Algol 68 Genie and a68j implement it; ga68 does not (Appendix C): it currently stops with an internal compiler error. The outputs shown are those of Algol 68 Genie; a68j prints the same values, in the narrower columns of its 32-bit int.

Leaving arguments out

With partial parametrization, a call may leave arguments out, by writing nothing in their places; the commas stay. Such a call does not run the function; it yields a new function that takes the missing arguments and has the given ones stored inside it:

proc add = (real x, y) real: x + y;
proc (real) real add3 = add (3, );
print ((fixed (add3 (4), 0, 1), " ", fixed (add (3, ) (10), 0, 1), newline))
7.0 13.0

add (3, ) is a function of one real, which adds 3. It can be called at once, as in add (3, ) (10), or kept and called later. The functional languages call the same idea partial application; in Python it is functools.partial, in C++ std::bind.

A function can be given its arguments in several stages. Each stage stores the new arguments and yields a function of the remaining ones:

proc volume = (real l, w, h) real: l * w * h;
proc (real, real) real base2 = volume (2, , );
proc (real) real base6 = base2 (3, );
print ((fixed (base6 (4), 0, 1), " ", fixed (base2 (1, 1), 0, 1), newline))
24.0 2.0

Closures without the lifetime problem

The stored arguments are part of the new function: they are copied into it, and the function does not refer to the block in which the call was made. This is what makes the idea work. Instead of using the names of an enclosing block, the inner function receives everything as parameters, and the outer function supplies them by partial parametrization. The function compose of Section 7.16, which Algol 68 Genie stops at run time there, becomes:

mode Fn = proc (real) real;
proc compose = (Fn f, g) Fn: ((Fn f, g, real x) real: f (g (x))) (f, g, );
proc double = (real x) real: 2 * x;
proc inc = (real x) real: x + 1;
Fn h = compose (double, inc);
print ((fixed (h (1), 0, 1), newline))
4.0

The inner function uses only its own parameters f, g and x. compose gives it the first two and returns the result, which no longer depends on compose’s parameters. Lindsey’s proposal shows the same pattern with an operator that raises the value of a function to a power, so that the cosine “squared” yields cos2θ. The operator ^ below instead applies a function n times:

mode Fn = proc (real) real;
proc iterate = (Fn f, int n, real x) real:
begin
   real y := x;
   to n do y := f (y) od;
   y
end;
prio ^ = 8;
op ^ = (Fn f, int n) Fn: iterate (f, n, );
proc half = (real x) real: x / 2;
print ((fixed ((half ^ 3) (1), 0, 3), " ", fixed ((cos ^ 20) (1), 0, 6), newline))
.125 .739184

Twenty applications of cos to 1 come close to the number x with cos x = x, 0.739085…; more applications get closer.

When the arguments are evaluated

The arguments of a call that leaves arguments out are evaluated when the call is made, not when the resulting function is finally called. A value is stored as it is at that moment; a reference is stored as a reference, so the function sees later changes of the variable it refers to:

proc add = (int a, b) int: a + b;
proc incr = (ref int c, int d) int: c +:= d;
int n := 1;
proc (int) int add_n = add (n, );
ref int counter = heap int := 0;
proc (int) int bump = incr (counter, );
n := 10;
print ((add_n (5), newline));
bump (1); bump (2);
counter +:= 100;
print ((bump (3), newline))
                  +6
                +106

add_n keeps the value 1 that n had when add_n was made; the later assignment to n does not change it. bump keeps the reference counter, and every call increases the same cell. A heap cell and a function that keeps a reference to it are the counter of Section 7.16 without the need to pass the counter along.

Pitfall.  The lifetime rule still applies to what is stored. A function made by partial parametrization lives only as long as both the original function and every value stored in it, whichever ends first. If a stored reference refers to a loc cell of a block, the function must not outlive that block:

proc incr = (ref int c, int d) int: c +:= d;
proc make_bump = proc (int) int:
begin
   loc int count := 0;
   incr (count, )
end;
proc (int) int bump = make_bump;
print ((bump (1), newline))
3        PROC incr = (REF INT c, INT d) INT: c +:= d;
                                             1       
a68g: runtime error: 1: REF INT value is exported out of its scope, in VOID closed-clause starting at "BEGIN" in line 1.

The cell count ends with the block of make_bump, and the function returned holds a reference to it. By the rules of the proposal, returning the function from the block is the error. Algol 68 Genie does not check it there; it stops the program only when the function is used, here in incr, whose result is the cell that no longer exists. a68j does not check the lifetime rule while the program runs (Section 7.15) and runs the program to the end, without a message. The counter must be a heap cell, as in the previous example.

Calls with all arguments

In Lindsey’s proposal, every call is a partial parametrization: a call that supplies all arguments yields a function without parameters, which is then called at once if the context requires a value, the usual case. If the context requires a function without parameters, the call is not executed but kept: proc int tick = incr (counter, 1) would declare a function that increases counter by 1 each time it is called.

Implementation note.  Algol 68 Genie and a68j do not implement this part of the proposal. They run a call as soon as all arguments are given, and reject the declaration of tick; Algol 68 Genie says:

5        PROC INT tick = incr (counter, 1);
                         1                 
a68g: error: 1: INT cannot be coerced to PROC INT in a strong-unit, in closed-clause starting at "BEGIN" in line 1.

Leaving out at least one argument, as bump does above, works in both.

A monad

Functional languages build computations with an effect, such as a result that may be missing or a choice among several results, as monads: a type M a of computations with results of type a, and an operation, bind, that runs a computation and passes each of its results to the next step. In Haskell Maybe and lists are monads; in Java Optional.flatMap and Stream.flatMap play the part of bind. (The word has nothing to do with the monadic operators of the Revised Report, the unary operators of this book.)

Algol 68 has no type parameters, so M a cannot be written once for every a. A monad can still be written that carries only the effect: the values stay in variables of the program, which the steps read and assign. A computation is then a function that calls its continuation, the rest of the computation, once for each result, or never:

mode M = proc (proc void) void;
prio BIND = 1;
op BIND = (M m, n) M: ((M m, n, proc void k) void: m (void: n (k))) (m, n, );
proc guard = (proc bool ok, proc void k) void: (ok | k);
proc act = (proc void a, proc void k) void: (a; k);

real x;
M safe = guard (bool: x /= 0, ) BIND act (void: x := 1 / x, )
   BIND guard (bool: x >= 0, ) BIND act (void: x := sqrt (x), )
   BIND guard (bool: x > 0, ) BIND act (void: x := ln (x), );
[]real tests = (-2, 0, 0.25, 1, 4);
for i to UPB tests do
   x := tests[i];
   bool done := false;
   safe (void: done := true);
   print (((done | fixed (x, 0, 6) | "undefined"), " "))
od;
print (newline)
undefined undefined .693147 .000000 -.693147

guard and act are steps: functions whose last parameter is the continuation. Given all other arguments, as in guard (bool: x /= 0, ), they yield a computation of type M. The operator BIND joins two computations as compose joins two functions: the result runs m with a continuation that runs n with the continuation k. The chain safe is made once and run for each test value. A guard that fails does not call its continuation, so the rest of the chain is skipped and done stays false: this is the Maybe monad. For −2 and 0 there is no result; for 0.25 the result is ln 2. The continuation is a parameter for the reason given in the previous section: a call with all arguments runs at once, so partial parametrization cannot make a function without parameters, and the argument left out is the continuation.

The same type M is the list monad when a step calls its continuation more than once. range assigns each number to its variable and continues with it; pythagorean continues only for Pythagorean triples, so it filters as guard does:

proc range = (ref int v, int lo, hi, proc void k) void:
   for i from lo to hi do v := i; k od;
proc pythagorean = (ref int a, b, c, proc void k) void:
   (a < b AND a * a + b * b = c * c | k);
proc triples = (ref int a, b, c, int n) M:
   range (a, 1, n, ) BIND range (b, 1, n, ) BIND range (c, 1, n, )
      BIND pythagorean (a, b, c, );

int a, b, c;
M t = triples (a, b, c, 20);
t (void: print (("(", whole (a, 0), " ", whole (b, 0), " ", whole (c, 0), ") ")));
print (newline)
(3 4 5) (5 12 13) (6 8 10) (8 15 17) (9 12 15) (12 16 20)

triples makes the chain and returns it. As in compose, no routine text in it uses the names of triples: the steps get the variables a, b and c as arguments, and these belong to the caller, which runs the chain while they exist.

Pitfall.  The steps get their arguments when the chain is made, not when it runs (“When the arguments are evaluated” above). This is why guard takes a proc bool and not a bool: a guard with a bool parameter would test x once, when safe is made. For the same reason range (b, a, n, ) would not count from the current value of a but store the value that a has when triples is called. Here a has no value yet: Algol 68 Genie stops with attempt to use an uninitialised INT value, and a68j runs with the initial value 0 (Section 2.5) and prints wrong triples. A step that needs the current value must get a function, as guard does, or the reference itself.

The effect of a Writer monad, a log written along the way, is not a choice of how to go on but a value that each step extends. It needs a type of its own: a computation takes the log so far and yields it extended, and bind is composition, again made by partial parametrization:

mode W = proc (string) string;
prio BIND = 1;
op BIND = (W f, g) W: ((W f, g, string log) string: g (f (log))) (f, g, );
proc note = (proc void a, string text, string log) string:
   (a; (log = "" | text | log + ", " + text));

real v := 5;
W golden = note (void: v := sqrt (v), "took the square root", )
   BIND note (void: v +:= 1, "added one", )
   BIND note (void: v /:= 2, "divided by two", );
print ((golden (""), newline));
print (("golden ratio ", fixed (v, 0, 6), newline))
took the square root, added one, divided by two
golden ratio 1.618034

The value 5 becomes (sqrt (5) + 1) / 2, the golden ratio, and the log tells how. Here the approach reaches its limits. Every effect needs its own type and its own BIND, and the two cannot be mixed in one chain. A log in a variable that act steps of type M extend would not help: all branches of a list computation would write into the same log. In all three examples the values do not travel in the monad but in variables, and the compiler does not check that a step reads what the previous step wrote; in Haskell the type M a does that.
