# Java integration: module ideas

The state of the Java integration (`-fnest-java`, `nest Java "…"` formal
holes, the modules `Lists` and `Hashmaps`) is described in
[java-modules.md](java-modules.md). This file collects ideas for further
modules backed by Java APIs. The open points of the integration itself
are done, and so are the idea B1, the modules `Texts` and `Regex`
([texts.md](texts.md), [regex.md](regex.md)), the idea B2, the module
`Files` ([files.md](files.md)), the idea B3, the modules `Bigints` and
`Bigdecimals` ([bigints.md](bigints.md), [bigdecimals.md](bigdecimals.md)),
and the idea B4, the module `Times` ([times.md](times.md)).

## Ideas for Java modules

Modules in the style of `Lists` and `Hashmaps`, where a Java API fills a
gap in the Algol 68 library (the prelude of the Revised Report and its
transput). They are ordered by how much they would help in everyday
programs, in my estimate.

Two rules from java-modules.md apply to all of them:

- A Java object is an opaque Algol 68 name, `mode X = ref X_object` with
  `mode X_object = struct (int x_java_object)`, as for `Stringlist`.
- A module that should be usable together with `Lists` must not declare
  a priority for `AT`, `INDEX`, `HAS` or `REMOVE`; it takes
  `access pub Lists` instead (java-modules.md, "`Lists` and `Hashmaps`
  together").

### B5. `Digests`: checksums and encodings

**The gap.** MD5, SHA-1, SHA-256, CRC-32 and Base64 need unsigned 32-bit
arithmetic and bytes, which Algol 68 expresses only with effort through
`bits`. Rosetta Code has `md5`, `crc-32` and `base64-encode-data`.

**The Java side.** `java.security.MessageDigest`, `java.util.zip.CRC32`,
`java.util.Base64`, `java.util.HexFormat`.

**How it fits.** A few procedures and no new modes: a digest of a string
(its UTF-8 bytes) as hexadecimal text, `crc32` as a `long int`, Base64
encoding and decoding of a string. Open question: whether bytes beyond
strings are needed (a row of `int`, or the contents of a file through
`Files`).

### B6. Priority queues and sorted maps

**The gap.** Dijkstra, A*, event simulation and "the k smallest" need a
heap or an ordered map; programs write their own each time.

**The Java side.** `java.util.PriorityQueue`, `java.util.TreeMap`.

**How it fits.** Modes generated by `tools/gen_lists.py` and
`tools/gen_hashmaps.py` or a generator next to them, for the element and
key modes of `Lists` and `Hashmaps`. The order is the natural one of the
mode; a queue of structures ordered by a field would need a key
procedure, as a priority of type `int` or `real` next to the element.
The rules above on `AT`, `INDEX`, `HAS` and `REMOVE` apply.

### B11. `Randoms`: random number generators

**The gap.** The only generator is `random` of the standard prelude:
glibc's `rand()` (TYPE_3, an additive lagged Fibonacci generator of
31 bits) that always starts with the seed 1, as in libga68, so that a68j
draws the same numbers as ga68 (`a68j.rt.Std`). `Genie_Transput` adds
`next_random` and `rnd` on top of it. A program cannot set the seed
(`first_random` of Algol 68 Genie is missing, genie-transput.md), there are
no integers in a range, no normal distribution and no shuffling of a row,
and there is one global state, which is synchronized once a PAR clause
has run (par-and-sema.md). 73 of the original Rosetta Code solutions use
`random` or `next random`, one `first random`; Monte Carlo methods,
shuffles and random mazes write their own helpers each time.

**The Java side.** `java.util.SplittableRandom`: fast, of good
statistical quality, and `split()` yields an independent generator, so
each unit of a PAR clause can have its own without a lock. Also
`java.util.random.RandomGenerator` for further algorithms. Not for
cryptography; `java.security.SecureRandom` is reachable directly through
`nest Java` where that is needed.

**How it fits.** A generator is a Java object, `mode Random =
ref Random_object`, made with a seed (reproducible runs) or without one.
Procedures on it: an `int` or `long int` in a range (`next_int (g, n)`
from 0 to n - 1, `next_int (g, lo, hi)`), a `real` or `long real` in
[0, 1), a `bool`, a normally distributed `long real` (`gaussian`),
`split (g)`, and shuffling a row in place (`shuffle`) for the element
modes of `Lists`. Optionally `first_random (seed)` for `-fgenie`, which
would make `random` reproducible with another seed; `random` itself stays
as it is, so that the output of a program stays the same as with ga68.
Open questions: the exact names, and whether the module offers a default
generator of its own next to the objects (procedures without `g`).

### B7. `Xml`: reading, querying and writing XML

**The gap.** A parser for XML in Algol 68 is much more work than one for
JSON: entities, namespaces, CDATA, encodings. Rosetta Code has
`XML/Output` for Algol 68, which needs no parser, but not `XML/Input`,
`XML/XPath` or `XML/DOM serialization`. Today a program reaches the JDK
only through `nest Java` holes (`DocumentBuilder::parse(InputSource)`,
java-modules.md).

**The Java side.** All in the JDK, no library needed:
`javax.xml.parsers` (DOM), `javax.xml.xpath`, `javax.xml.transform`
(serialization).

**How it fits.** A mode `Xml_node` (`org.w3c.dom.Node`): parse a string
or a file, name, text and attributes of a node, its children as a row,
XPath queries that yield a row of nodes or strings, creating elements,
and the text of a document. Open questions: namespaces (left out at
first?), and whether parse errors are runtime errors or a result that
the program tests.

### B8. Images

**The gap.** Algol 68 has no graphics. Programs write PPM or SVG files
by hand; the bitmap tasks of Rosetta Code build their images in Algol 68
(`PR READ "prelude/Bitmap.a68"`).

**Algol 68 Genie.** Genie draws with GNU plotutils, if built with it
(`src/a68g/rts-plotutils.c`, names in `prelude-extern.c`); the build of
3.13.4 in WSL has no plotutils. A file is a drawing device:
`make device (f, type, size)` (also `draw device`) with the type `"X"`
(a window), `"gif"`, `"pnm"`, `"png"` or `"ps"` and a size such as
`"600x400"`, then `open (f, name, stand draw channel)`, and `close (f)`
writes the file. The procedures take the file first: `draw move`,
`draw line`, `draw point`, `draw rect`, `draw circle`, `draw ball`,
`draw star` and `draw text` at coordinates from 0 to 1 (scaled by the
size; a line or rectangle starts at the last position); `draw colour`
and `draw background colour` with red, green and blue from 0 to 1,
`draw colour name` with a name of X11's `rgb.txt`; `draw linestyle`,
`draw linewidth`, `draw fillstyle`, `draw fontname`, `draw fontsize`,
`draw textangle`, `draw erase` (`draw clear`), `draw show`
(`draw flush`), `draw aspect` and `draw possible`. Only 4 Rosetta Code
originals use them, 3 of them with a window (`dragon-curve-3`,
`hello-world-graphical`, `window-creation-x11`) and 1 with a GIF
(`mandelbrot-set`).

**The Java side.** `java.awt.image.BufferedImage`, `java.awt.Graphics2D`,
`javax.imageio.ImageIO` (PNG, GIF), headless.

**How it fits.** A mode for an image with pixels, lines, rectangles,
circles and text, written to a PNG file. The procedures of Algol 68
Genie would need `stand draw channel` and devices in the transput of
`Genie_Transput`; for 4 programs, that is hardly worth it.

### B9. External processes

**The gap.** Running a command and reading its output. The command-line
arguments are covered by the POSIX module of ga68; `system` of Algol 68
Genie (`execute-a-system-command`) is not available.

**The Java side.** `java.lang.ProcessBuilder`.

**How it fits.** A procedure that runs a command (a row of strings, no
shell) and yields its exit status, one that also yields its standard
output as a string, and `system` of Algol 68 Genie for `-fgenie`. Small,
but rarely needed.

### B10. Less central

HTTP (`java.net.http.HttpClient`) and JSON would also fit technically.
JSON has no parser in the JDK, so it would need a library on the class
path (`-fjava-classpath`). Both are less central for Algol 68 programs.
